## 5. Key Engineering Decisions & Invariants

### 5.1 No Unrestricted AI Editing
The system strictly prohibits "AI edit the entire repository" behavior. All modifications must be discrete, bounded file patches with verified unified diffs. Proposals affecting more than `maxFilesLimit` (default 10) or more than `maxTotalLinesChanged` (default 500) are blocked.

### 5.2 Multi-Pattern Denylist & Allowlist Guardrails
Security-sensitive files are automatically denylisted (`.git/**`, `.github/**`, `.fps/**`, `**/*.env`, `**/*.key`, `**/*.lock`, `build/**`, `.dart_tool/**`). Custom allowlists (e.g. `lib/**`) can be applied to further confine modifications.

### 5.3 Multi-Stage Verification Pipeline Before Eligibility
Before a proposal is marked `isEligibleForApplication: true`, it must pass all 4 verification gates:
1. **Patch Syntax Validity**: Unified diff headers and hunk coordinates are structurally valid.
2. **Automated Tests**: Test suite passes with 0 regressions.
3. **Dart Analyzer Check**: Static analysis reports 0 errors.
4. **Code Formatter Check**: Proposed Dart code satisfies standard formatting rules.

### 5.4 Mandatory Human Execution Approval
Even when a proposal passes all verification gates, `applyModification` refuses execution unless `explicitApproval: true` is provided (or `--confirm` in CLI).

### 5.5 Atomic Snapshots & Zero-Loss Rollback
Before applying any change, exact byte snapshots of target files are written to `.fps/backups/<proposalId>/` along with a manifest. `rollbackModification` can revert the workspace to its exact prior state at any time.

### 5.6 Secret Scrubbing
Outbound prompts, proposed patches, unified diffs, and rendered reports are scrubbed with `SecretRedactor` to prevent credential exposure.
