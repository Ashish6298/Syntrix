EXPLICIT STORAGE ISOLATION CONFIRMATION
----------------------------------------
The Plugin State Persistence Subsystem (`PluginStateStore`) maintains STRICT PHYSICAL AND STRUCTURAL ISOLATION from existing package metadata and core project state files:
- Dedicated Isolated Storage Path     : `<project_root>/.fps/plugins/plugins_state.json`
- Dedicated Isolated Storage Directory: `<project_root>/.fps/plugins/`
- Existing Core Metadata (Untouched)  : `pubspec.yaml`, `pubspec.lock`, `CHANGELOG.md`, `README.md`, `lib/**`, `test/**`
- Existing Template Metadata (Untouched): `<project_root>/.fps/template_metadata.json`

This isolation is enforced as an architectural boundary: `PluginStateStore` never reads, mutates, merges, or overwrites any core project documents or metadata files outside its dedicated `.fps/plugins/` namespace.

  PERSISTENCE ARCHITECTURE & ATOMIC-WRITE SAFETY AUDIT

1. PERSISTED STATE CATEGORIES:
   Captures upstream subsystem results with zero duplication:
   - `enabled/disabled` state (`isEnabled: bool`)
   - `version` (`SemVer` from Phase 6.1/7.1)
   - `validationResult` (`PluginValidationResult` from Phase 7.1)
   - `compatibilityResult` (`DependencyResolutionResult` from Phase 7.6)
   - `redactedConfiguration` (`RuntimeConfiguration` from Phase 7.5; secrets are strictly redacted before serialization)
   - `lifecycleState` (`PluginLifecycleState` from Phase 7.7)
   - `lifecycleHistory` (`List<LifecycleTransitionRecord>` from Phase 7.7)
   - `failureRecords` (`List<ExecutionAuditRecord>` from Phase 7.7/7.9)
   - `lastKnownGoodSnapshot` (Fallback configuration snapshot for upgrade failure recovery)

2. SAFE BY CONSTRUCTION ATOMIC WRITES & AUDIT:
   Writes state documents using an atomic write pattern through `FileUtils`:
   - Step 1: Serialize document with SHA-256 integrity checksum to isolated temporary file (`plugins_state.json.tmp.<microseconds>`).
   - Step 2: Atomic rename/move (`FileUtils.rename()`) into the canonical location (`plugins_state.json`).
   - Step 3: Catch-and-clean up temporary file on failure.

   AUDIT OF ATOMIC WRITE TESTING & OS RELIANCE:
   - Test 4a verifies that an exception thrown during temporary file writing (prior to rename) aborts cleanly, leaving any pre-existing canonical state untouched and valid.
   - Test 4b verifies the harder and more critical boundary: an interruption occurring AFTER the temporary file has been fully written and flushed, but DURING the rename/move operation. Tested via test seam `_SimulatedFailedRenameFileUtils`, which throws at the `rename()` invocation and leaves the temporary file behind. Verified that:
     (a) The original canonical state remains intact and loadable with its previous valid content.
     (b) The temporary file is never mistaken for or loaded as canonical state.
     (c) Subsequent reads return the last known-good state with zero partial or corrupt hybrid mutations.
   - OS-Level Reliance: The atomicity of the final step relies on the operating system filesystem's native atomic `rename()` / `MoveFileEx` semantics for same-filesystem moves (POSIX standard atomic rename semantics).

3. EXPLICIT RECOVERY PATHS IMPLEMENTATION:
   - Corrupt Plugin State   : Checksum mismatch or JSON parse failure is flagged as `corruptState` without crashing the core; requires re-discovery.
   - Failed Initialization  : Plugins with `initializationFailed` or `shutdownFailed` are surfaced explicitly without auto-retrying activation.
   - Invalid Configuration  : Mismatches against current schema are flagged as `invalidConfiguration`; prevents broken auto-activation.
   - Plugin Removal         : Persisted entries missing from disk discovery are flagged as `orphanedRemoved` rather than dangling references.
   - Plugin Upgrade Failure : Upgrades that fail contract checks trigger fallback reporting to `lastKnownGoodSnapshot`.
   - Ambiguity Fail-Closed  : Non-restorable or unrecognizable states are treated as unsafe/inactive.
