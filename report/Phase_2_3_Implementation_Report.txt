PHASE 2.3 OBJECTIVES
---------------------
  Extend the local Phase 2.2 catalog into a secure, provider-based, remote-
  capable Template Marketplace architecture that can:
    - Discover catalog metadata from remote registries over HTTPS
    - Merge remote results with local providers deterministically
    - Validate remote metadata before it enters the catalog
    - Handle network failures gracefully with stale-cache fallback
    - Cache safely with configurable TTL
    - Protect users from malicious / malformed registry data
    - Provide professional CLI management commands
    - Preserve all existing Phase 1.1–2.2 functionality

MODULE: src/marketplace/
------------------------
  A new, fully isolated module in flutter_package_studio_core. All marketplace
  types are exported from marketplace.dart and exposed through the core barrel.
  No existing module (catalog, template, github, etc.) was modified — only
  exceptions.dart was extended with new exception types.

NETWORK: RegistryTransport (Abstract Interface)
-----------------------------------------------
  No new pub.dev dependency was introduced. The RegistryTransport interface is
  pure Dart (no dart:io HTTP). All tests use MockRegistryTransport or
  MutableMockRegistryTransport (both in-process, fully synchronous/async).
  A real HTTP implementation can be injected by the CLI layer in a future phase.

CACHING: Memory-only (Phase 2.3)
---------------------------------
  Disk caching is deferred intentionally. Phase 2.3 uses RegistryMetadataCache
  (TTL-based, in-memory). Extension point: swap the cache store behind
  RegistryManager without changing the public API.

CONFLICT RESOLUTION: First-wins, explicit, documented
------------------------------------------------------
  1. Builtin/local providers (registered first in TemplateDiscoveryService)
     take priority. The TemplateCatalog.merge() call processes providers in
     registration order; remote provider is registered last.
  2. Among remote registries, first-registered registry wins for duplicate
     id@version keys (RegistryManager.allValidatedRecords deduplication loop).
  3. Remote registries cannot claim "builtin" category (rejected by validator).

PROTOCOL: FPS Registry Protocol v1
------------------------------------
  GET <baseUrl>/catalog → JSON response:
    { "protocolVersion": "1",
      "registryId": "...",
      "generatedAt": "ISO-8601",
      "templates": [ { ... metadata fields ... } ] }
  Unknown protocol versions → RegistryProtocolException (rejected at parse).
  No executable content in protocol. Metadata discovery only.

SECURITY MODEL
--------------
  Layer 1: RemoteRegistryOptions
    - HTTPS scheme enforced; http://, file://, etc. rejected
    - SSRF protection: localhost, 127.x, 10.x, 192.168.x, 172.16–31.x blocked
    - Registry ID validated: ^[a-z][a-z0-9_-]{0,63}$
  Layer 2: RegistryResponseParser
    - Protocol version guard (must equal "1")
    - JSON structure validation (object root, array templates)
    - Non-object array elements silently skipped
  Layer 3: RemoteMetadataValidator
    - Template ID: ^[a-z][a-z0-9_]{0,63}$
    - Version: strict TemplateSemVer.parse()
    - displayName: non-empty, max 128 chars
    - description: max 512 chars
    - projectType: only allowedProjectTypes set
    - category: remote cannot claim "builtin"
    - maturity: in allowedMaturityValues
    - tags/capabilities: each matches ^[a-z][a-z0-9_-]{0,63}$
    - dependency IDs: same as template ID pattern
    - documentationUrl: HTTPS only, valid URI
    - downloadCount: >= 0
    - rating: 0.0–5.0
    - minimumDartSdk: non-empty, constraint character prefix
  Layer 4: RegistryMetadataCache
    - Credentials are never stored
    - Stale reads re-serve validated data (no re-validation bypass)
  Layer 5: RemoteCatalogProvider
    - Template.fileTemplates and binaryTemplates are always empty for remote
      entries (metadata-only; no executable content)
    - Credentials never appear in catalog entries

================================================================================
  KNOWN LIMITATIONS & INTENTIONALLY DEFERRED CAPABILITIES
================================================================================

1. DISK CACHING DEFERRED
   Phase 2.3 uses memory-only caching. Cache survives the lifetime of a single
   CLI invocation. Disk-based persistent caching is a clear future extension
   point (implement a DiskRegistryCacheStore behind the same API).

2. REAL HTTP TRANSPORT NOT PROVIDED
   RegistryTransport is abstract. Production HTTP (dart:io HttpClient or http
   package) must be injected by the CLI layer. This is intentional: the core
   package remains dependency-free for testing.

3. TEMPLATE ACQUISITION NOT IMPLEMENTED
   Phase 2.3 provides metadata discovery only. Remote template file downloading,
   installation, and execution are explicitly excluded and deferred to a future
   acquisition phase (2.x or 3.x). This is a security boundary decision.

4. AUTHENTICATION PROVIDERS LIMITED
   RegistryAuthMode enum defines bearerToken mode but no active credential
   resolution is implemented in Phase 2.3 (no real registry endpoint to auth
   against). Environment-based credential injection is the designed model for
   future implementation.

5. DEFAULT PUBLIC REGISTRY NOT DEFINED
   No production registry endpoint is hardcoded. Users add registries via
   "fps registry add". Tests use MockRegistryTransport exclusively.

6. SERVER-SIDE SEARCH NOT IMPLEMENTED
   Phase 2.3 fetches the full catalog index and performs client-side filtering.
   Server-side search API (query parameters) is a protocol extension for later.
