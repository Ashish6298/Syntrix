## 5. Key Engineering Decisions

### 5.1 Dual-Key Schema Compatibility
**Problem**: `AssistantEngine` enforced `"steps"` in the planning JSON schema; the Phase 8.11 domain model uses `"implementationSteps"`.  
**Solution**: Extended `_parseAndValidatePayload` to accept either `"steps"` OR `"implementationSteps"`, normalizing to `"steps"` before passing to `PlanningPayload.fromJson`. This is backwards-compatible with any prior planning consumers.

### 5.2 Grounding Invariant: Facts vs. Assumptions
The engine seeds the `requirementAnalysis` with workspace-verified facts before calling the AI, then merges AI-provided items, de-duplicating by text equality. This guarantees at least one verified fact is always present and clearly labelled.

### 5.3 Read-Only Safety Invariant
The engine performs zero filesystem writes. All workspace interaction is through `ProjectContextEngine.discoverProject()` and `Directory.listSync()` (read-only operations). Test 5 verifies this by comparing filesystem state before and after planning.

### 5.4 HTML Escaping in Renderer
All user-controlled string fields (objective, scope, fact text, step descriptions, etc.) are passed through `_escapeHtml()` before being written into the Markdown output. This prevents `<script>`, `<img>`, or heading injection attacks via malicious engineering request strings.

### 5.5 Secret Redaction: Triple-Layer Defence
1. **Prompt level**: `SecretRedactor.redact(prompt)` before sending to AI provider
2. **Response level**: `SecretRedactor.redact(objective)` and `SecretRedactor.redact(scope)` in `_parsePlanResponse`
3. **Output level**: `SecretRedactor.redact(...)` as the final operation in both `renderJson` and `renderMarkdown`
